# Scheduler test plan

**266 behaviours**: 124 tested, 115 untested, 27 unclear. Risk: 92 high, 138 medium, 36 low.

<!-- counts:end -->

For comparison, the Modbus Bridge's plan (its PR #217): **238 behaviours**: 130 tested,
93 untested, 15 unclear. The row-by-row comparison is
[Scheduler parity](scheduler-parity.md).

The input for the Scheduler test phase. Every behaviour documented in
[User guide → Scheduler](../guide/scheduler/index.md) carries a hidden marker in the page
source with its code location, its current test (or *untested* / *unclear*) and whether it
can write to a battery. The table below is generated from those markers. The format and the
columns are the Modbus Bridge's, so the two plans line up; the behaviour ids match where the
two bridges document the same thing.

## How to read it

| Column | Meaning |
|---|---|
| **#** | Behaviour id. The prefix names the page: IDX overview, CON concepts, TRG triggers, CND/SEN conditions, ACT/HAA actions, TGT targets, EXT exit, PRI priorities, OUT outcomes, RST/CLK restarts and clock. An id shared with the Modbus Bridge's plan is the same topic; numbers above that plan's highest per prefix are Direct Connect only. |
| **Risk** | **high**: can write to a battery and no test covers it (or the code is unclear). **medium**: can write to a battery but is tested, or cannot write but is untested or unclear. **low**: cannot write and is tested. |
| **Code** | File and lines under `src/franklinwh_direct_connect_bridge/`. |
| **Current test** | The unit test that asserts it, or **untested** / **unclear** (the code is ambiguous or looks wrong; the test decides). A behaviour is marked tested only when the named test was read and asserts it. |
| **Proposed test** | **unit**: pytest against `scheduler.py` with the store in a temporary SQLite file and `battery_control.execute` monkeypatched, as in `tests/test_scheduler.py`. **unit (API)**: FastAPI `TestClient` against the app. **browser**: Playwright against a throwaway bridge. **VM/mock**: a throwaway bridge (HAOS test VM or `docker-compose.demo.yml`) with a mock gateway. |
| **Battery write** | Whether the behaviour decides if, when or how a force, release, operating-mode, reserve or off-grid command reaches a gateway. |

The table is ordered by risk, then *unclear* before *untested* before *tested*.

!!! danger "Test safely"
    Battery-write tests run against a **mock gateway** or the Direct Connect library's
    `Emulator` on a throwaway bridge, never a real aGate and never the owner's live bridge.
    A force command in this bridge goes through the Modbus client (this bridge) to the
    Modbus TCP Server (aGate :502); a test of that path needs the FranklinWH Gateway
    Emulator or a monkeypatched `battery_control.execute`, as the existing tests do.
    *unclear* rows marked as likely defects should be written as tests that state the
    expected behaviour and fail today; fixes come after.
