Why the Bridge exists

A working example of the Direct Connect API, grown into a full app

The Bridge started as a reference implementation of FranklinWH's local Direct Connect API. The goal was a REST API with an OpenAPI specification that a user interface could be built on, to run and administer an aGate and its aPowers: first one gateway, then several. Home Assistant support and scheduling were built on that foundation.

Baseline

Default setup

Bridge + your aGate over the local Direct Connect API. No cloud account, no broker.

You needaGate on the LAN with a fixed IP. Nothing to enable on the gateway.
  • Live power flow, SoC, mode and run status
  • Per-cell BMS voltages and temperatures, with recorded sessions
  • Several gateways from one install, with LAN discovery
  • Local SQLite history, charts, Analytics and CSV export
  • Scheduler, tariffs and billing, solar forecast
  • Writes stay off until you enable them
HA add-onDockerPython 3.11+
No hardware

Mock setup

Seeded emulated aGates bundled in the image, with solar, battery and load that follow the time of day.

You needDocker. One demo command starts it.
  • See the whole UI working before you connect real hardware
  • Two mock gateways ready for multi-gateway testing
  • Control buttons enabled safely against the mock
  • Kept apart from a real install, with its own data and MQTT off
  • Good for demos, screenshots and UI work
Optional transport

FranklinWH Cloud

The FranklinWH cloud API. Used only where the local API can't reach.

You needA FranklinWH account and internet. Included in the add-on and Docker image.
  • Reserve SoC write (the aGate discards it locally)
  • Cloud-native mode and smart-circuit setters
  • The Bridge shows which transport handles each feature
Optional transport

Modbus TCP

SunSpec Modbus on the aGate, from FranklinWH's published PICS plus register extensions FranklinWH supplied.

You needModbus switched on in the aGate, and the Bridge's Modbus client turned on in Settings.
  • Force charge or discharge at a set power
  • Optional target SoC to stop at
  • Bridge watchdog and a global Release, so a dropped link can't leave the battery dispatched
  • No separate Modbus Bridge service needed
  • Modbus reachability shown in Health
Publish out

MQTT broker

Publishes each aGate as a native Home Assistant device through MQTT discovery. No custom integration.

You needA broker. As an add-on it auto-configures from Mosquitto, even one installed later.
  • Sensors, binary sensors, selects and switches in HA
  • Offline gateways show as unavailable, not stale
  • Republish, unpublish and per-group entity control
  • Broker scan for other FranklinWH publishers
Read in

Home Assistant integration

The Bridge links to one or more HA instances over HA's REST API and reads from them.

You needNothing as an add-on (linked automatically). Elsewhere: HA URL and a long-lived token.
  • Use any HA entity as a Scheduler entry or exit condition
  • Call HA services from schedules
  • Setup checks that tell you what is missing
  • Dashboard-card YAML generator
Alert you

Home Assistant notifications

Pushes to your phone through the HA Companion app, plus persistent notices in HA.

You needA linked Home Assistant and the Companion app on your phone.
  • aGate offline or back online
  • Off-grid started or ended
  • Battery dispatch the Bridge didn't start (VPP)
  • SoC below or above your thresholds
  • In HA: Modbus down, cloud sign-in rejected, firmware changed, aGate moved IP

Which FranklinWH API? The cloud transport is FranklinWH's own cloud API, the same one the FranklinWH app uses, reached through the franklinwh-cloud library. That library was based on and inspired by richo's franklinwh-python library and the ha-franklinwh HACS integration, with most endpoints discovered using HTTP Toolkit. It comes with the add-on and Docker image.
